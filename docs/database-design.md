# Database Design — Campus Lost-and-Found System

**Team:** Solid Squad  
**Milestone:** 3 — Working Prototype and Design Evidence  
**Backend:** Django ORM (Python)  
**Current development database:** SQLite  
**Planned database:** PostgreSQL

## 1. Purpose and scope

The database supports the implemented prototype flow: a student reports a found item, another student submits an ownership claim, and the claim can be approved or rejected. The data model also records notification events for later processing. The prototype uses Django's built-in authentication user model rather than a custom university SSO implementation.

The current implementation is a Django modular monolith with three feature apps: `items`, `claims`, and `notifications`. All three share one relational database.

## 2. Entity overview

| Entity / Django table | Main fields | Responsibility |
| --- | --- | --- |
| User / `auth_user` | `id`, `username`, `email` (selected fields) | Represents the reporter or claimant. Django manages additional user fields. |
| Item / `items_item` | `id`, `reporter_id`, `title`, `description`, `found_location`, `status`, `created_at` | Stores a reported found item. |
| Claim / `claims_claim` | `id`, `item_id`, `claimant_id`, `reason`, `status`, `created_at` | Stores a request to claim ownership of an item. |
| NotificationOutbox / `notifications_notificationoutbox` | `id`, `claim_id`, `event_type`, `status`, `created_at`, `processed_at` | Records a notification event for possible later delivery. |

Primary keys are generated by Django. Foreign-key fields connect records across apps; all domain tables are persisted through the Django ORM.

## 3. Relationships

- **User 1:N Item:** `Item.reporter` points to the user who reported the item.
- **User 1:N Claim:** `Claim.claimant` points to the user who submitted the claim.
- **Item 1:N Claim:** one reported item may receive claims from different users.
- **Claim 1:N NotificationOutbox:** a claim may have distinct events such as created, approved, and rejected.

The foreign keys use `on_delete=PROTECT` to prevent deleting referenced objects through the Django ORM while related records remain. This preserves the claim and notification history.

## 4. Integrity rules and statuses

| Rule | Implementation | Effect |
| --- | --- | --- |
| A user cannot submit two claims for the same item | `UniqueConstraint(item, claimant)` | Rejects duplicate claim rows, including after a previous rejection. |
| A claim cannot have two notifications of the same event type | `UniqueConstraint(claim, event_type)` | Prevents duplicate outbox events of the same type for one claim. |
| Referenced users, items, and claims are protected from deletion | Foreign keys with `on_delete=PROTECT` | Preserves related records during ORM deletion. |
| A reporter cannot claim their own item | `claims.services.create_claim()` | Application-level validation; not a database constraint. |
| Only available items can receive new claims | `claims.services.create_claim()` | Application-level validation using `Item.Status.AVAILABLE`. |

Current model status values:

- **Item:** `AVAILABLE`, `CLAIMED`, `RETURNED`.
- **Claim:** `PENDING`, `APPROVED`, `REJECTED`.
- **NotificationOutbox:** `PENDING`, `SENT`, `FAILED`.
- **Notification events:** `CLAIM_CREATED`, `CLAIM_APPROVED`, `CLAIM_REJECTED`.

The claim lifecycle uses the **State pattern** in `claims/states.py`: approving a pending claim changes its status to `APPROVED` and marks the corresponding item as `CLAIMED`. The service layer creates the relevant outbox records. The database does not itself enforce every workflow transition.

## 5. Implementation and verification

The schema is defined in `items/models.py`, `claims/models.py`, and `notifications/models.py`, with versioned migrations inside each app's `migrations/` directory. Models are registered in Django Admin to support manual inspection and record creation.

To apply the schema and run the database tests from the `src` directory:

```bash
python manage.py migrate
python manage.py test claims notifications -v 2
```

The automated database tests cover successful creation, duplicate-claim rejection, protected deletion of an item with a claim, creation of an outbox entry, and duplicate-notification rejection. They use Django's isolated test database and do not call external messaging services.

## 6. Current limitations and next steps

- SQLite is used for the current prototype, while PostgreSQL remains the planned persistent store. PostgreSQL migration and performance targets have not been verified by these database tests.
- The notification outbox stores events, but it does **not** by itself implement asynchronous dispatch, retries, or email/push delivery.
- University SSO and matching services are planned, not part of the implemented database scope described here.
- **Migration consistency:** The original `items` initial migration stores older item-status choices (`Available` and `ClAIMED`), while the current model defines `AVAILABLE` and `CLAIMED`. Before deployment or shared-data migration, add and test a follow-up schema/data migration to normalize existing rows. Coordinate that change with the backend team to avoid breaking status-based filters.

The current prototype demonstrates relational persistence and data integrity. End-to-end API and user-interface evidence should be documented separately by the respective team members.
